### 2.2 Resolve CSS and theme isolation before global adoption

The current app uses Tailwind/coss theme variables and `ThemeProvider attribute="class"`. Arc expects `<html data-theme="dark">`, uses overlapping variable names, and its foundation contains global `:root`, body, and focus rules. A wrapper around the dashboard alone cannot isolate those rules. A route-level dynamic import also does not guarantee that CSS disappears when navigating away.

The preferred implementation spike is a single root-managed Arc foundation stylesheet link, active for dashboard routes only, alongside a bridge that mirrors the existing resolved theme to Arc's `data-theme` and sets an explicit `data-accent`. Build the stylesheet from the installed foundation without editing vendor selectors. Keep the app's existing stylesheet link and load order explicit. Verify direct SSR entry, client navigation into and out of the dashboard, overlays portalled to body, and return to public routes. Treat route-controlled stylesheet behavior as unproven until measured in the actual TanStack Start build.

If root-managed activation cannot preserve SSR, focus styles, and public styling, keep rollout blocked at the foundation spike and decide on an isolated stylesheet build or a separately approved global theme migration. Do not ship a global theme rewrite as an incidental dashboard change. Import or link the foundation exactly once through the chosen root mechanism.

Load the existing Geist font and Inter with Arc's expected `--font-geist` and `--font-inter` inputs. Inspect actual font loading before adding packages because this repository already has Geist and Inter dependencies. Arc headings at 30px or larger use Geist. Body, controls, and smaller headings use Inter. Keep weights to 400 and 500. Preserve the special typography of the resume and cover-letter documents.

### 3.1 Preserve advanced filtering

`ListSearchBar` currently combines debounced text, draft/incomplete chips, operators, RSQL-backed URL state, sorting, and clear behavior. Arc `filter-toolbar` models field/value facets, not a general RSQL builder.

Use Arc `search-field` for `q` and `select` for display sort. Use `filter-toolbar` only for fields/operators that round-trip exactly. Keep the existing Cubby filter controls for unsupported operators, ranges or incomplete drafts. Both paths must serialize through the existing core contracts. Do not replace `between`, negation, multi-value or numeric operations with approximate equality chips. Clearing must cancel stale debounced text and clear committed and draft filters.

### 3.2 Preserve authoritative sort and selection

Arc `sortable-data-table` exposes column rendering, selection and `onSortChange`, but its `defaultSort` is initial state and its built-in sort operates on supplied rows. It is not documented as a fully controlled server-sort table.

For complete small admin result sets, use Arc sorting directly. For paginated/infinite job and catalog results, keep server ordering authoritative. Use externally controlled sort with non-sortable Arc headers if the product can preserve its current controls. Otherwise retain the incumbent table/list renderer. Do not remount the table on every sort to reset `defaultSort`, because that loses focus and animation continuity. Preserve stable selection IDs, hidden selections, batch actions, and the distinction between visible count and total count.

### 3.3 Preserve global entity search

The free `command-palette` documents an items array but no controlled query or query-change callback. The app's current palette performs asynchronous SQL entity search and deliberately avoids client-refiltering those results.

Keep the existing global command renderer/controller unless the installed Arc API has gained a documented hook that supports server query, loading, and pass-through ranking. Use the Arc palette only for a separate static command collection if that is truly needed. Do not replace the main palette with a static-only list or attach a second global Mod+K handler. Pro `search-results` and `ai-search-bar` do not establish parity with the current command system by their names alone.

### 9.3 Apply the Arc visual and interaction rules

One `h1` per page, hierarchical section headings, meaningful landmarks and one primary action per active surface. Use sentence case and no uppercase eyebrow labels. No ornamental gradients, glows, repeated tilt or icon tiles. Use semantic tokens, 400/500 weights and tabular numerals for changing values. Prefer proximity and dividers before another card.

Check 320, 390, 768, 1024 and 1440px, plus both sides of the existing 1280px desktop-panel breakpoint. Use one scroll owner per pane. Tables/code/board overflow is contained and reachable; the document itself must not accidentally scroll sideways. Controls tapped on touch have at least 44px targets. Hover-only affordances always have keyboard/tap access.

Keep Arc's shared keyboard focus styles and visible input/listbox states. Do not remove keyboard focus to achieve a ringless mouse appearance. Give fields labels/errors, icon buttons specific names, overlays a title and reliable focus return, and live work a suitable status announcement. Check text contrast at least 4.5:1 and controls/graphics at least 3:1; apply the actual WCAG large-text exception only at qualifying size/weight. The vendor guide's 18.5px medium wording does not justify treating 500-weight small text as large.

Use Arc smooth state motion without overshoot and reduced-motion branches. Keep stable component keys and avoid reading browser-only values during the first render. Do not copy Next.js server-component assumptions into TanStack Start.

Compare both themes and neutral plus one saturated accent. Resume/letter papers retain their document-specific rendering contract even when surrounding UI uses Arc.
