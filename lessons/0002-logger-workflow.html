The evlog Logger Workflow

How wide events flow from Hono to your oRPC handler — and how to fix the missing .emit()

Lesson 2 · 15–20 min · logging

Your Mission

In Lesson 1 you traced the data flow from GitHub API → cache → oRPC → UI. This lesson digs into the logging infrastructure — how the monorepo records what happened during each request. By the end you will:

  • Understand the three logger types and when to use each
  • Trace the full flow: Hono middleware → oRPC context → your handler

  • Be able to add proper logging to any function or oRPC procedure

The evlog Model: "Wide Events"

This project uses evlog v2.18 — a "wide event" logger. Instead of writing one line per log call (like pino or winston), evlog lets you accumulate context throughout a request and flush it all at once as a single rich JSON object. 

// Wide event pattern:
logger.set({ user: { id: "abc", plan: "pro" } });
logger.set({ cart: { items: 3, total: 49.99 } });
logger.emit({ status: 200 });
// → one event: { user: {...}, cart: {...}, status: 200, duration: 142, ... }

This is the opposite of per-line logging. You call .set() repeatedly as you move through the request, and the middleware calls .emit() automatically when the response is sent. The result: one wide event per request, with all the context you care about.

The Three Logger Types

RequestLogger

Created by Hono middleware per-request. Auto-correlated with method, path, requestId, duration, and status. .emit() is called automatically by the middleware. Available in oRPC procedures as context.logger.

Use inside: oRPC handlers, route handlers, middleware

Standalone (createLogger)

Manual logger for jobs, background tasks, or functions called outside request context. You must call .emit() yourself — the event is silently dropped otherwise. No auto-populated HTTP fields.

Use inside: getRepoOverview, cron jobs, webhook handlers

Global log

Singleton facade. Fire-and-forget: each call flushes immediately. Use for one-off events that aren't part of a request. No .emit() needed.

Use for: server startup, caches misses, health check results

See the evlog API Reference for the full method signatures.

Full Flow: RequestLogger from Hono → oRPC

Open these files as we trace the logger from middleware to handler:

1. apps/server/src/app.ts:50-58 — honoLoggerMiddleware() runs on every request. Creates a RequestLogger, stored as c.get("log"). Starts a duration timer.
2. apps/server/src/app.ts:210-211 — The route handler calls createContext({ context: c, logger: c.get("log") }). This extracts the logger from Hono's context and passes it into oRPC context.
3. packages/api/src/lib/context/types.ts:1-9 — OrpcContext declares logger: RequestLogger as a field.
4. packages/api/src/lib/context/hono/create-context.ts:16-35 — createContext() receives the Hono context and logger, builds the OrpcContext object, and returns it.
5. packages/api/src/lib/procedures/factory.ts:5-7 — publicProcedure uses os.$context<OrpcContext>() so every procedure's handler receives context.logger.
6. Your procedure handler — receives context.logger. Call .set(), .info(), .error() as needed.
7. apps/server/src/app.ts:200-208 — On error, oRPC interceptor fires: context.logger.set({ handler: "rpc" }) and context.logger.error(error).
8. Hono responds. evlog middleware auto-calls .emit(). Logger is sealed — no more mutations.
Key insight: Steps 1-6 mean context.logger is available on literally every publicProcedure and protectedProcedure handler. But currently, no procedure in the codebase uses it. The only procedure that logs (health.live) uses the global log instead, which doesn't correlate with the request context.

The Bug in getRepoOverview

Open packages/github/src/repo/get-repo-overview.ts.

On line 16, a standalone logger is created:

const logger = createLogger({ source: "github.repo.getRepoOverview" });

On lines 27-30, the early-return path sets context but never emits:

if (!source.isConfigured) {
  logger.set({ handler: "getRepoOverview" });
  logger.set("GitHub source is not configured.", { reason: source.reason });
  // 🚫 No logger.emit() here — event is silently dropped!
  return null;
}

Bug: Missing .emit()

evlog's standalone logger does not auto-flush. Without .emit(), the context is accumulated but never sent to any drain (console, Axiom, etc.). evlog emits a console warning about this, but no wide event is ever produced.

Fix: Add logger.emit() before returning.

Also notable: this logger is created at module scope (line 16). It's reused across all calls to getRepoOverview, so context from one call could bleed into another. Better practice: create it inside the function, or use the request-scoped logger from the caller.

Fixing the Bug

Here's the corrected pattern for the early-return path:

if (!source.isConfigured) {
  const logger = createLogger({ source: "github.repo.getRepoOverview" });
  logger.set({ handler: "getRepoOverview", owner: input.owner, repo: input.repo });
  logger.set("GitHub source is not configured.", { reason: source.reason });
  logger.emit({ status: 200 });  // ← Flushes the event
  return null;
}

The Better Pattern: Thread the RequestLogger

Since getRepoOverview is always called from an oRPC procedure (which has context.logger), the ideal approach is to accept an optional RequestLogger and use it when available, falling back to a standalone logger: 

import { type RequestLogger } from "@tsu-stack/logger/server";

export async function getRepoOverview(
  input: { owner: string; repo: string },
  runtime?: GitHubRuntimeBindings,
  requestLogger?: RequestLogger  // ← new param
): Promise<GitHubRepoOverview | null> {
  const log = requestLogger ?? createLogger({ source: "github.repo.getRepoOverview" });

  const source = await resolvePublicGitHubSource();
  if (!source.isConfigured) {
    log.set({ handler: "getRepoOverview", owner: input.owner, repo: input.repo });
    log.set("GitHub source is not configured.", { reason: source.reason });
    log.emit({ status: 200 });
    return null;
  }
  // ... rest of function
}

Then in the oRPC procedure, pass context.logger:

.handler(async ({ input, context }) => {
  return getRepoOverview(input, context.github, context.logger);
})

This way, when called from a request, the logging is correlated with the enclosing HTTP request (method, path, requestId, duration). When called outside request context, the standalone logger handles itself.

Caveat: RequestLogger + .emit()

If you call context.logger.emit() manually inside getRepoOverview, it will seal the logger. The middleware's later .emit() becomes a no-op. To avoid this, use context.logger.set() and .info()/.warn()/.error() to accumulate sub-events, and let the middleware handle the final emit.

Putting It Together: In an oRPC Procedure

Here's how you'd actually use context.logger in a procedure handler:

getRepoOverview: publicProcedure
  .route({ method: "GET", path: "/repos/:owner/:repo/overview" })
  .input(inputSchema)
  .handler(async ({ input, context }) => {
    // Add context to the request's wide event
    context.logger.set({
      owner: input.owner,
      repo: input.repo,
      feature: "repo-overview"
    });

    // Record a sub-event inside this request
    context.logger.info("Fetching repo overview");

    try {
      const result = await getRepoOverview(input, context.github);

      // Don't call .emit() — middleware handles it.
      // You can still call .set() to add more context:
      context.logger.set({ cached: result.meta?.fresh ?? false });

      return result;
    } catch (error) {
      context.logger.error(error);
      // Middleware will still emit with status derived from the oRPC error
      throw error;
    }
  })

The emitted wide event would look like:

{
  "method": "GET",
  "path": "/rpc/github/repo/overview",
  "owner": "salah",
  "repo": "portfolio-v2",
  "feature": "repo-overview",
  "duration": 423,
  "status": 200,
  "requestLogs": [
    { "level": "info", "message": "Fetching repo overview", "timestamp": "..." }
  ],
  "service": "server",
  "environment": "development",
  "version": "abc123"
}
