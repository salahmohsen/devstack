The evlog Model: "Wide Events"

This project uses evlog v2.18 — a "wide event" logger. Instead of writing one line per log call (like pino or winston), evlog lets you accumulate context throughout a request and flush it all at once as a single rich JSON object. 

// Wide event pattern:
logger.set({ user: { id: "abc", plan: "pro" } });
logger.set({ cart: { items: 3, total: 49.99 } });
logger.emit({ status: 200 });
// → one event: { user: {...}, cart: {...}, status: 200, duration: 142, ... }

This is the opposite of per-line logging. You call .set() repeatedly as you move through the request, and the middleware calls .emit() automatically when the response is sent. The result: one wide event per request, with all the context you care about.

The Three Logger Types

RequestLogger

Created by Hono middleware per-request. Auto-correlated with method, path, requestId, duration, and status. .emit() is called automatically by the middleware. Available in oRPC procedures as context.logger.

Use inside: oRPC handlers, route handlers, middleware

Standalone (createLogger)

Manual logger for jobs, background tasks, or functions called outside request context. You must call .emit() yourself — the event is silently dropped otherwise. No auto-populated HTTP fields.

Use inside: cron jobs, replay scripts, background tasks

Global log

Singleton facade. Fire-and-forget: each call flushes immediately. Use for one-off events that aren't part of a request. No .emit() needed.

Use for: server startup, caches misses, health check results

See the evlog API Reference for the full method signatures.

Full Flow: RequestLogger from Hono → oRPC

Open these files as we trace the logger from middleware to handler:

1. apps/server/src/app.ts:50-58 — honoLoggerMiddleware() runs on every request. Creates a RequestLogger, stored as c.get("log"). Starts a duration timer.
2. apps/server/src/app.ts:210-211 — The route handler calls createContext({ context: c, logger: c.get("log") }). This extracts the logger from Hono's context and passes it into oRPC context.
3. packages/api/src/lib/context/types.ts:1-9 — OrpcContext declares logger: RequestLogger as a field.
4. packages/api/src/lib/context/hono/create-context.ts:16-35 — createContext() receives the Hono context and logger, builds the OrpcContext object, and returns it.
5. packages/api/src/lib/procedures/factory.ts:5-7 — publicProcedure uses os.$context<OrpcContext>() so every procedure's handler receives context.logger.
6. Your procedure handler — receives context.logger. Call .set(), .info(), .error() as needed.
7. apps/server/src/app.ts:200-208 — On error, oRPC interceptor fires: context.logger.set({ handler: "rpc" }) and context.logger.error(error).
8. Hono responds. evlog middleware auto-calls .emit(). Logger is sealed — no more mutations.
Key insight: Steps 1-6 mean context.logger is available on literally every publicProcedure and protectedProcedure handler. In the GitHub stack, handlers now pass full request context into the package readers, and those readers enrich context.logger through helper functions. The most visible remaining gap is health.live, which still uses global log and therefore skips request correlation.

    reason: source.reason
  });
  return null;

Why this is better

The GitHub reader no longer owns emission. It enriches the request logger when one is available, and the Hono middleware still performs the single final .emit().

The Preferred Pattern

For request-backed GitHub readers, accept request context and update the shared logger instead of creating a nested standalone logger. Reserve createLogger() for work that has no request wrapper at all. 

export async function getRepoOverview(
  input: { owner: string; repo: string },
  context?: OrpcContext
): Promise<RepoOverview | null> {
  setRepoLoggerContext(context, "getRepoOverview", {
    owner: input.owner,
    repo: input.repo
  });

  // ... continue using setRepoLoggerOutcome()/setRepoLoggerLocalFirstOutcome()
}

Then in the oRPC procedure, pass the whole request context through:

.handler(async ({ input, context }) => {
  return getRepoOverview(input, context);
})

Caveat: RequestLogger + .emit()

If you call context.logger.emit() manually inside getRepoOverview, it will seal the logger. The middleware's later .emit() becomes a no-op. To avoid this, use context.logger.set() and .info()/.warn()/.error() to accumulate sub-events, and let the middleware handle the final emit.

Putting It Together: In an oRPC Procedure

Here's the current shape of a request-aware handler pattern:

getRepoOverview: publicProcedure
  .route({ method: "GET", path: "/repos/:owner/:repo/overview" })
  .input(inputSchema)
  .handler(async ({ input, context }) => {
    context.logger.set({
      owner: input.owner,
      repo: input.repo,
      feature: "repo-overview"
    });

    context.logger.info("Fetching repo overview");

    try {
      const result = await getRepoOverview(input, context);

      context.logger.set({
        cacheStatus: result?.__meta?.cacheStatus ?? null
      });

      return result;
    } catch (error) {
      context.logger.error(error);
      // Middleware will still emit with status derived from the oRPC error
      throw error;
    }
  })

The emitted wide event would look like:

{
  "method": "GET",
  "path": "/rpc/github/repo/overview",
  "owner": "salah",
  "repo": "portfolio-v2",
  "feature": "repo-overview",
  "duration": 423,
  "status": 200,
  "requestLogs": [
    { "level": "info", "message": "Fetching repo overview", "timestamp": "..." }
  ],
  "service": "server",
  "environment": "development",
  "version": "abc123"
}
