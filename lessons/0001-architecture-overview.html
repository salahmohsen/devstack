GitHub Wrapper Architecture

Mapping the territory before you dig in

Lesson 1 · 15–20 min · architecture

Your Mission

The @tsu-stack/github package is a full-featured GitHub API wrapper with caching, real-time invalidation, and a complete frontend UI. By the end of this lesson, you will be able to trace a complete data flow from the GitHub API through the cache layer, the oRPC router, the server, and into the React frontend.

This is the most important lesson in the series — once you have this mental model, every subsequent lesson will feel like filling in details on a map you already know.

The Four Layers

The GitHub integration is split across four packages/apps in the monorepo:

⬇ @tsu-stack/github Core: Octokit client, cache engine, typed fetchers, webhook handler
⬇ @tsu-stack/api oRPC: Public + private procedures, Zod schemas
⬇ apps/server Hono routes, webhook endpoint, Durable Object relay
⬇ apps/web TanStack Start routes, React Query hooks, signal stream (WS)

Data flows down this stack (GitHub API → UI) and back up through webhooks and signal streams (GitHub → invalidation → UI refresh).

Trace a Data Flow: Repo Overview

Let's trace one concrete example: rendering a repository overview page. Open these files as we walk through each layer.

Layer 1: Core Package

packages/github/src/repo/repo-overview/get-repo-overview.ts

This file exports getRepoOverview(input, context?). It:

  1. Calls resolvePublicGitHubSource() to get the configured token + owner
  2. Creates an Octokit instance via createGitHubOctokit(source)
  3. Calls getGitHubResourceLocalFirst() — the central cache function
  4. Inside that cache function: checks KV cache, then DB cache, then GitHub API
  5. The actual API call is a GraphQL query (for full repo details + languages + topics)
  6. Records request-scoped logging metadata when context.logger is present
  7. Returns RepoOverview | null

Key insight: every data-fetching function in this package follows the same pattern — resolve source, create client, call cache orchestrator.

Layer 2: oRPC Procedures

packages/api/src/routers/public/github/index.ts

The getRepoOverview procedure (line 363):

getRepoOverview: oRPC
  .route({ method: "GET", path: "/repos/:owner/:repo/overview" })
  .input(getRepoOverviewSchema)
  .handler(async ({ input, context }) => {
    return getRepoOverview(input, context);
  })

It passes the full oRPC context into the core package so the reader can use both runtime bindings and request-scoped logging helpers. This is still a thin adapter layer.

Layer 3: Server

apps/server/src/app.ts

The Hono server mounts the oRPC handler. It also serves:

  • POST /webhooks/github — receives GitHub webhook events
  • Durable Object-backed WebSocket relay for GitHub invalidation signals

The server layer is responsible for runtime bindings: KV store, Durable Object namespace, execution context. These are injected via c.env.

Layer 4: Frontend

apps/web/src/pages/github-repo/api/get-github-repo-overview.query.ts

The React Query hook calls the oRPC procedure:

export function getRepoOverviewQueryOptions(input: RepoInput) {
  return queryOptions({
    queryKey: ["github", "repo", "overview", input],
    queryFn: () => client.public.github.getRepoOverview(input),
    staleTime: 1000 * 5, // 5 seconds — matches cache policy
  });
}

Route files preload data with ensureQueryData() where needed, and page components consume the same query options with standard React Query hooks.

The Cache Engine

The heart of the system is packages/github/src/infrastructure/cache/github-cache.ts (366 lines). Here's the decision flow: 

getGitHubResourceLocalFirst(options):
  1. Check KV cache for fast hit
  2. Check DB cache for durable hit
  3. If fresh (within staleTimeMs): return immediately
  4. If stale but within gcTimeMs:
     a. Check if namespace version changed
     b. Check if revalidation signal is newer than fetchedAt
     c. If either: treat as miss (refetch from API)
     d. Otherwise: refetch with ETag/If-None-Match
        - On 304: extend staleAt, return cached data
        - On 200: update cache, return new data
        - On 403/429: return stale data as fallback
  5. If past gcTimeMs: fresh fetch from API (no conditional)

This is a stale-while-revalidate pattern with namespace-based and signal-based invalidation. The two invalidation mechanisms:

  • Namespaces — version counters bumped by webhook events. When a namespace version differs, all entries in that namespace are stale.
  • Signals — ownerActivity:{owner}, repoCode:{owner}/{repo}, etc. Timestamp-based. When a signal timestamp is newer than the entry's fetchedAt, that specific entry is stale.

The Real-Time Invalidation Loop

When something happens on GitHub (e.g., a push to a repo):

  1. GitHub sends a webhook to POST /webhooks/github
  2. handleGitHubWebhook() verifies the HMAC signature
  3. It computes signal keys from the event type (e.g., repoMeta:owner/repo for a push event)
  4. It bumps cache namespaces and marks revalidation signals in the DB
  5. It broadcasts to the GitHubSignalRelay Durable Object
  6. The DO sends a WebSocket message to all connected clients
  7. The client's useGitHubSignalStream hook receives the message
  8. It calls queryClient.invalidateQueries() for matching query keys
  9. React Query refetches the data (which hits the cache layer — ETag likely returns 304)

This is the loop that keeps the UI fresh, with a 20-second fallback sync implemented inside useGitHubSignalStream when WebSocket delivery is missed.

Key Patterns to Remember

  • Every GitHub function follows: resolve source → create Octokit → call cache orchestrator
  • Cache policy is set per data category (contributions can be 15 min stale; activity is 5 seconds)
  • The core package is runtime-agnostic — Cloudflare bindings are an optional parameter
  • The oRPC layer is thin — just schema validation + passthrough
  • Webhooks drive invalidation — the real-time loop is the most architecturally interesting part
